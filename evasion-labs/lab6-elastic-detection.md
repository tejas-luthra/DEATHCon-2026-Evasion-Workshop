# Lab: Detecting the Shellcode Loader Attack in Elastic

## Overview

In this lab you will use Kibana Discover to search the Sysmon telemetry generated by the shellcode loader attack from the previous lab. You will build and run three detection filters that cover two stages of the attack chain — payload delivery over HTTP and credential access against LSASS — and examine the raw event data that each filter surfaces. By the end of the lab you will understand why each filter fires, what the key fields mean, and how the same logic applies to real-world frameworks like Cobalt Strike and Brute Ratel.

## Background: What the Attack Does

`loader.exe` is a binary that sits on disk in `C:\Windows\Tasks\` with no shellcode embedded. When executed it makes an outbound HTTP connection to the attacker's server, pulls down a mimikatz shellcode payload at runtime, loads it directly into memory, and executes it. The shellcode opens a handle to LSASS — the Windows process that holds credential material — and reads password hashes and Kerberos tickets out of its memory.

The whole operation generates three detection-relevant events in Sysmon:

| Sysmon Event | ID | What it captures |
|---|---|---|
| NetworkConnect | 3 | `loader.exe` connecting to the C2 server over HTTP |
| ProcessAccess | 10 | The shellcode opening a handle to `lsass.exe` |
| ProcessAccess | 10 | Repeated handle duplication calls as the shellcode extracts credentials |

This is the same pattern used by professional red team frameworks. Cobalt Strike, Brute Ratel, and Havoc all use a lightweight loader or beacon on disk with the actual capability delivered over the network and executed in memory. The detection surface is identical — the filters you build in this lab catch all of them.

## Part 1: Open Kibana Discover

### Step 1 — Navigate to Kibana

Open your browser and go to the DEATHCon 2026 Kibana instance. Use the URL and credentials provided in your workshop materials.

Log in and from the left-hand navigation menu select **Discover** (the compass icon).

### Step 2 — Set the Data View

In the top-left of the Discover interface, click the data view dropdown. Select:

```
logs-windows.sysmon_operational-*
```

If this data view is not listed, click **Create a data view** and enter the index pattern manually.

> 📝 **Note:** All three filters in this lab target this data view exclusively. Sysmon operational events are stored here by the Elastic Agent's Windows integration.

### Step 3 — Set the Time Range

In the top-right corner, click the time picker and select **Last 24 hours** (or widen the range if you ran the attack more than 24 hours ago). Confirm that events are present — you should see activity in the histogram.

### Step 4 — Understand the Key Fields

Before running any filters, expand any event in the results list by clicking the arrow on the left. The fields you will use in this lab are:

| Field | Description |
|---|---|
| `event.code` | Sysmon event ID (3 = NetworkConnect, 10 = ProcessAccess) |
| `winlog.event_data.TargetImage` | The process being accessed (Event 10) |
| `winlog.event_data.GrantedAccess` | The access permissions requested (Event 10) |
| `winlog.event_data.CallTrace` | The call stack at the time of access (Event 10) |
| `process.executable` | The full path of the process making the request |
| `process.name` | The filename of the process making the request |
| `destination.ip` | The remote IP address (Event 3) |
| `destination.port` | The remote port (Event 3) |

## Part 2: Filter 1 — Unusual Process Making Outbound HTTP Connection

This filter catches the delivery stage of the attack — the moment `loader.exe` reaches out to pull down the shellcode payload. It fires before any credential access takes place.

### Step 1 — Enter the Filter

Click the KQL search bar at the top of Discover and paste the following:

```
event.dataset:"windows.sysmon_operational" and event.code:"3" and destination.port:(80 or 8080) and not process.name:("chrome.exe" or "firefox.exe" or "msedge.exe" or "iexplore.exe" or "MicrosoftEdge.exe" or "svchost.exe" or "wuauclt.exe" or "MoUsoCoreWorker.exe" or "SearchApp.exe" or "taskhostw.exe" or "msiexec.exe" or "teams.exe" or "OneDrive.exe" or "code.exe" or "curl.exe" or "python.exe" or "python3.exe")
```

Press **Enter** or click **Refresh**.

### Step 2 — Examine the Results

You should see one or more hits from `loader.exe`. Expand a result and confirm:

| Field | Expected Value |
|---|---|
| `event.code` | `3` |
| `process.name` | `loader.exe` |
| `process.executable` | `C:\Windows\Tasks\loader.exe` |
| `destination.ip` | Your Kali/attacker IP |
| `destination.port` | `8080` |
| `network.protocol` | `tcp` |

### Step 3 — Understand Each Filter Element

**`event.code:"3"`** — Sysmon Event 3 is a NetworkConnect event. It fires every time a process opens an outbound network connection and records the process name, destination IP, and port.

**`destination.port:(80 or 8080)`** — We filter for plain HTTP ports specifically. Attackers use HTTP for payload staging because it passes through most firewalls without deep packet inspection. Port 8080 is a common C2 port. In a Cobalt Strike deployment you would see the beacon making HTTP callbacks to its team server on a similar port.

**`not process.name:(...)`** — This exclusion list is what makes the filter usable in production. Without it, every browser request and Windows Update check would appear in the results. By excluding known-good HTTP clients, anything remaining is a process with no business making outbound HTTP connections. `loader.exe` is not on the list. Neither would a Cobalt Strike beacon named `svchost32.exe` or a custom implant dropped as `update.exe`.

> 📝 **Note:** This filter fires at the earliest point in the attack chain — before LSASS is ever touched. In a real environment this is your opportunity to block the attack before credentials are exposed.

## Part 3: Filter 2 — LSASS Access with UNKNOWN CallTrace

This filter catches the execution stage — the moment the shellcode runs against LSASS. It is the highest-fidelity filter in this lab because it directly fingerprints shellcode execution.

### Step 1 — Why Not CreateRemoteThread?

You might expect a shellcode attack on LSASS to generate a CreateRemoteThread alert — Sysmon Event 8, a process injecting a thread into another process. During the development of this lab that rule never fired. The reason: this loader does not inject a thread into LSASS. It opens LSASS, reads memory directly, and exits. No thread creation occurs, so Event 8 is never generated. Investigating what *did* fire led to this filter — which turns out to be more precise anyway.

### Step 2 — Enter the Filter

Clear the previous search and paste:

```
event.dataset:"windows.sysmon_operational" and event.code:"10" and winlog.event_data.TargetImage:*lsass.exe and winlog.event_data.CallTrace:*UNKNOWN*
```

Press **Enter**.

### Step 3 — Examine the Results

You should see over a thousand hits, all from `loader.exe`. Expand a result and confirm:

| Field | Expected Value |
|---|---|
| `event.code` | `10` |
| `process.executable` | `C:\Windows\Tasks\loader.exe` |
| `winlog.event_data.TargetImage` | `C:\Windows\System32\lsass.exe` |
| `winlog.event_data.CallTrace` | `...ntdll.dll+...\|...KERNELBASE.dll+...\|UNKNOWN(0x...)` |
| `winlog.event_data.GrantedAccess` | `0x40`, `0x1400`, or `0x1010` |

### Step 4 — Understand Each Filter Element

**`event.code:"10"`** — Sysmon Event 10 is ProcessAccess. It fires whenever one process opens a handle to another. To read credentials out of LSASS an attacker *must* open a handle to it — there is no way around this step. That is what makes Event 10 the foundation of LSASS detection.

**`winlog.event_data.TargetImage:*lsass.exe`** — LSASS is the Local Security Authority Subsystem. It holds NTLM hashes, Kerberos tickets, and in some configurations plaintext credentials in memory. Every credential dumping tool — mimikatz, ProcDump, Cobalt Strike's `hashdump` command — must access it.

**`winlog.event_data.CallTrace:*UNKNOWN*`** — When Sysmon logs a ProcessAccess event it also captures the call stack — the chain of return addresses that led to the LSASS open call. For legitimate software every address maps back to a known module loaded from disk: `ntdll.dll`, `kernelbase.dll`, the application binary itself. `UNKNOWN` means the return address points to memory with no backing file on disk — heap-allocated memory. That is shellcode.

> 📝 **Note:** The high hit count (1,000+) is expected. The shellcode makes over 1,100 handle duplication calls (`GrantedAccess: 0x40`) as part of the credential extraction loop, plus one memory read (`0x1400`) and one secondary read (`0x1010`). Every hit is from `loader.exe` with an UNKNOWN return address — zero false positives.

### Step 5 — Confirm All Hits Are from loader.exe

Add a column for `process.executable` by clicking the field in the left sidebar and selecting **Add column**. Scroll through the results and confirm every row shows `C:\Windows\Tasks\loader.exe`. This same UNKNOWN CallTrace pattern appears when Cobalt Strike or Brute Ratel beacon commands inject shellcode into a sacrificial process that then accesses LSASS.

## Part 4: Filter 3 — LSASS Access with Credential-Dump GrantedAccess Mask

This filter catches a different class of attacker: someone running a credential dumping tool directly from disk rather than injecting shellcode. It uses the same Event 10 and LSASS target as Filter 2, but detects via known-bad access masks instead of CallTrace content.

### Step 1 — Enter the Filter

Clear the previous search and paste:

```
event.dataset:"windows.sysmon_operational" and event.code:"10" and winlog.event_data.TargetImage:*lsass.exe and (winlog.event_data.GrantedAccess:"0x1010" or winlog.event_data.GrantedAccess:"0x1FFFFF" or winlog.event_data.GrantedAccess:"0x143A" or winlog.event_data.GrantedAccess:"0x1038" or winlog.event_data.GrantedAccess:"0x1410")
```

Press **Enter**.

### Step 2 — Examine the Results

You should see hits covering both the shellcode loader and any mimikatz runs from earlier in the lab. Expand a result and note the `winlog.event_data.GrantedAccess` value.

### Step 3 — Understand the GrantedAccess Masks

When a process opens a handle it must declare exactly what it wants to do with it. That declaration is recorded as the GrantedAccess mask. These five values are documented credential dumping signatures:

| Mask | Permissions | Associated Tool |
|---|---|---|
| `0x1010` | PROCESS_QUERY_LIMITED_INFORMATION + PROCESS_VM_READ | mimikatz `sekurlsa::logonpasswords` — the most widely recognised credential dumping mask |
| `0x1FFFFF` | PROCESS_ALL_ACCESS | Unsophisticated tools that request full control rather than specific rights |
| `0x143A` | VM_READ + VM_WRITE + VM_OPERATION + PROCESS_QUERY_INFORMATION + CREATE_THREAD | Tools that inject code into LSASS; seen in some Cobalt Strike configurations |
| `0x1038` | PROCESS_QUERY_LIMITED_INFORMATION + VM_OPERATION + VM_READ + VM_WRITE | Custom dumpers and some Brute Ratel modules |
| `0x1410` | PROCESS_QUERY_LIMITED_INFORMATION + PROCESS_QUERY_INFORMATION + VM_READ | A mimikatz variant mask used by several open-source post-exploitation frameworks |

### Step 4 — Understand the Tradeoff vs Filter 2

Filter 2 (UNKNOWN CallTrace) is surgical — it only fires on shellcode executing from memory with no disk backing. Filter 3 (GrantedAccess) is broader — it catches mimikatz running as a binary on disk, ProcDump, and any tool requesting these access mask combinations. The tradeoff is that Filter 3 can fire on legitimate security software such as antivirus engines that scan LSASS for threats. In this lab environment you may see Windows Defender (`MsMpEng.exe`) appear in the results.

> 📝 **Note:** In a production SOC both rules run simultaneously. Filter 2 drives high-confidence automated response (the UNKNOWN CallTrace is a near-certain indicator of shellcode). Filter 3 drives analyst triage — the hits need a quick review to separate legitimate security tooling from actual attacks.

## What a Successful Lab Looks Like

| Check | Expected Result |
|---|---|
| Filter 1 (Event 3) | At least one hit from `loader.exe` to attacker IP on port 8080 |
| Filter 1 exclusion | No hits from browsers, svchost, or Windows Update processes |
| Filter 2 (UNKNOWN CallTrace) | 1,000+ hits, all from `loader.exe`, all with `UNKNOWN(0x...)` in CallTrace |
| Filter 2 false positives | Zero — no legitimate processes appear |
| Filter 3 (GrantedAccess) | Hits from `loader.exe` with masks `0x40`, `0x1010`, `0x1400` |
| Filter 3 false positives | Possible hit from `MsMpEng.exe` (Windows Defender) — expected |

## Common Errors and Fixes

| Error | Cause | Fix |
|---|---|---|
| No results for any filter | Logs were cleared before the lab | Re-run the shellcode loader attack from Lab 3, then return to Part 1 |
| Filter 1 returns no hits | Loader ran before the Elastic Agent enrolled | Re-run the attack; the agent only forwards new events, it does not backfill |
| Filter 1 returns hundreds of hits | Exclusion list not applied correctly | Check for typos in the `not process.name:(...)` clause; parentheses and quotes must be exact |
| Filter 2 returns zero hits | CallTrace field not mapped | Expand any Event 10 document and confirm `winlog.event_data.CallTrace` is present; if missing, check the Sysmon config version |
| Filter 3 returns only Defender hits | Mimikatz was not run in this session | Hits from `MsMpEng.exe` with mask `0x1010` are expected Windows Defender behaviour — add `and not process.name:"MsMpEng.exe"` to exclude them |
| Data view not available | Index pattern not created | In Kibana go to **Stack Management → Data Views** and create a view for `logs-windows.sysmon_operational-*` |
| Time range shows no data | Attack ran outside the selected window | Widen the time range picker to cover the time the attack was executed |
