# Lab: Visibility Basics - Analyzing Malicious Payloads with ThreatCheck

## Overview

In this lab, you will run a known malicious tool (Mimikatz) in a controlled environment, observe how Windows Defender and Windows Event Logs respond, and then use **ThreatCheck** to identify the exact bytes that trigger Defender's static signatures. By the end, you will understand *why* a payload gets flagged and where the detection boundary lives.

---

| Requirement | Details |
|---|---|
| OS | Windows 10/11 (VM recommended) |
| Permissions | Local Administrator |
| Tools | ThreatCheck, Mimikatz, Windows Defender (real-time protection **enabled**) |
| Network | Isolated/host-only network adapter recommended |

> ⚠️ **Warning:** Perform this lab inside an isolated virtual machine only. Do **not** run Mimikatz on production or domain-joined systems.

## Lab Goals

- Observe Defender's real-time response to a malicious binary
- Identify relevant Windows Event Log entries generated by the detection
- Use ThreatCheck to pinpoint the static signature bytes that trigger Defender
- Understand the difference between static and behavioral detections

## Part 1: Running Mimikatz and Observing Defender

### Step 1 - Prepare the Environment

Snapshot your VM before starting so you can revert cleanly.

Confirm Windows Defender real-time protection is **on** - the value should return `False`:
```powershell
Get-MpPreference | Select-Object DisableRealtimeMonitoring
```
Open an elevated PowerShell prompt, then add `C:\Lab-Artifacts` as a Defender exclusion so the lab tools are not quarantined while you work:
```powershell
Add-MpPreference -ExclusionPath "C:\Lab-Artifacts"
```

> This mirrors a real-world scenario where an attacker controls their staging directory. Defender will still monitor every other path on the system - which is exactly what you will trigger in Step 3.

### Step 2 - Locate Mimikatz

Mimikatz is already present on your lab VM at `C:\Lab-Artifacts\Mimikatz\mimikatz.exe`.

**NOTE:** if Mimikatz is missing or quarantined by Defender you can use 7-Zip to extract mimikatz.exe from `C:\Lab-Artifacts\Mimikatz\mimikatz.7z`. The password is ==3v4sion==

### Step 3 - Trigger a Detection

Windows Defender's real-time protection scans files **when they are written to disk**, however copying a file from an excluded source will be an exception. You will now deliberately copy Mimikatz to a path outside the exclusion zone and then execute it to trigger a detection.

```powershell
Copy-Item "C:\Lab-Artifacts\Mimikatz\mimikatz.exe" -Destination "C:\Windows\Temp\mimikatz.exe"
```

```powershell
C:\Windows\Temp\mimikatz.exe
```

Watch for the Defender toast notification: **"Threats found"**. Defender will quarantine the file.

Confirm the detection fired:

```powershell
Get-MpThreatDetection | Select-Object -Last 5 | Format-List
```

**Expected output fields to note:**

- `ThreatName` - e.g. `HackTool:Win64/Mikatz!dha`
- `ActionSuccess` - should be `True`
- `DetectionSourceTypeID` - `3` indicates real-time protection
- `Resources` - should show the `C:\Windows\Temp\` path, confirming it was the copy that triggered the detection, not the original file

> 📝 **Execution detection:** Defender flagged the binary the moment it was executed from `Windows\Temp`. This is a static signature match against the file's bytes on disk. The source file at `C:\Lab-Artifacts` was untouched because of the exclusion you added in Step 1.

## Part 2: Reviewing Windows Defender and Event Logs

### Defender Logs - Windows Security Center

Open **Windows Security → Virus & threat protection → Protection history** to view the quarantine event in the GUI.

### Windows Event Log - Key Event IDs

Open Event Viewer (`eventvwr.msc`) and navigate to:

```
Applications and Services Logs
  └── Microsoft
        └── Windows
              └── Windows Defender
                    └── Operational
```

| Event ID | Description                                                                   |
| -------- | ----------------------------------------------------------------------------- |
| **1116** | Malware detected - includes threat name, severity, path, and detection source |
| **1117** | Action taken on malware (quarantine, remove, etc.)                            |
| **1006** | Scan found malware                                                            |
| **5001** | Real-time protection disabled (useful for detecting tampering)                |

#### Filtering for Relevant Events

In PowerShell:

```powershell
Get-WinEvent -LogName "Microsoft-Windows-Windows Defender/Operational" |
  Where-Object { $_.Id -in @(1116, 1117) } |
  Select-Object TimeCreated, Id, Message |
  Format-List
```

**What to look for in Event ID 1116:**

- `Threat Name` - the AV signature name
- `Path` - full path to the detected file
- `Detection Origin` - Local machine, network share, etc.
- `Detection Type` - `Concrete` = static/signature match; `FastPath` = cloud lookup

> 📝 **Note:** A `Detection Type` of `Concrete` confirms this is a **static signature** match - exactly what ThreatCheck will help you analyze in Part 3.

## Part 3: Analyzing the Payload with ThreatCheck

### What is ThreatCheck?

ThreatCheck (by [rasta-mouse](https://github.com/rasta-mouse/ThreatCheck)) works by binary-searching a file - repeatedly splitting it in half and submitting each chunk to the AV engine - until it isolates the **smallest byte range** that triggers the detection. It supports both AMSI and Windows Defender as scan backends.

### Step 1 - Set Up ThreatCheck

`ThreatCheck.exe` is located at `C:\Lab-Artifacts\ThreatCheck\ThreatCheck.exe`. The `C:\Lab-Artifacts` exclusion you added in Part 1 already covers this directory, so ThreatCheck will not be quarantined.

### Step 2 - Run ThreatCheck Against Mimikatz

ThreatCheck.exe will place a temporary instance of the file in `C:\Temp\File.exe`. Because of this  an exemption needs to be created for Defender:
```powershell
Add-MpPreference -ExclusionPath "C:\Temp"
```

The original Mimikatz binary at `C:\Lab-Artifacts\mimikatz.exe` is still intact (only the copy to `Windows\Temp` was quarantined). Run ThreatCheck directly against it:

```cmd
C:\Lab-Artifacts\ThreatCheck\ThreatCheck.exe -f C:\Lab-Artifacts\Mimikatz\mimikatz.exe -e Defender
```

**Flags:**

| Flag | Description |
|---|---|
| `-f` | Path to the file being analyzed |
| `-e` | Scan engine: `Defender` or `AMSI` |
| `-t` | (Optional) Specify threat type filter |

### Step 3 - Interpret the Output

ThreatCheck will print output similar to:

```
[+] Target file size: 1,258,496 bytes
[+] Analyzing...
[*] Testing 629248 bytes - Detected
[*] Testing 314624 bytes - Detected
[*] Testing 157312 bytes - Detected
...
[!] Identified end of bad bytes at offset 0x3B200
[*] Dumping 256 bytes from offset 0x3B100

  Offset    00 01 02 03 04 05 06 07  ANSI
  --------  -----------------------  ----
  0x3B100   6D 69 6D 69 6B 61 74 7A  mimikatz
  0x3B108   00 73 65 6B 75 72 6C 73  .sekurls
  ...
```

**What this tells you:**

- **Offset** - where in the binary the signature match ends
- **Hex dump** - the raw bytes that caused the detection
- **ANSI column** - readable strings embedded in those bytes (e.g. `mimikatz`, `sekurlsa`, `lsadump`)

These strings are the **static indicators** Defender's signature is keying on. In this case, plaintext tool-identifying strings compiled into the binary are sufficient for detection - no execution required.

## ⭐ Bonus Lab: Build Mimikatz from Source and Strip Signatures Iteratively

> **This is a bonus lab.** Complete it only after finishing Parts 1–3. It is self-paced and goes significantly deeper - expect to spend 30–60 minutes or more depending on how many signature iterations you work through.

### Overview

In this bonus section you will compile Mimikatz from its public source code, run ThreatCheck against your freshly built binary, locate the offending bytes in the source, patch them, rebuild, and repeat. The goal is not to produce a weaponized tool - it is to develop an intuition for **how AV signatures are anchored to source-level artifacts** and how many independent signatures a single project can carry.

> 📦 **Note:** A pre-built copy of Mimikatz is already available at `C:\Lab-Artifacts\Mimikatz\mimikatz.exe` for the main lab exercises. The build steps here are intentional - compiling from source is part of the learning experience - but if you are short on time you may use the pre-built binary starting at Step 3.

> ⚠️ **Warning:** Keep this work inside your isolated VM. Do not transfer modified binaries to production systems or share them. This exercise is purely for understanding detection engineering.

### Prerequisites

| Requirement | Details |
|---|---|
| Visual Studio 2022 (Community OK) | Install the **"Desktop development with C++"** workload |
| Git for Windows | To clone the repository |
| ThreatCheck | Already present at `C:\Lab-Artifacts\ThreatCheck\ThreatCheck.exe` |
| Defender exclusions | You will add them per-step below |

### Step 1 - Clone the Mimikatz Source

Open an elevated Developer Command Prompt (search "Developer Command Prompt for VS 2022") and run:

```cmd
cd C:\Lab-Artifacts
git clone https://github.com/gentilkiwi/mimikatz.git mimikatz-src
```

Add the source tree and your build output folder to Defender's exclusion list so it doesn't quarantine files as you work:

```powershell
Add-MpPreference -ExclusionPath "C:\Lab-Artifacts\mimikatz-src"
Add-MpPreference -ExclusionPath "C:\Lab-Artifacts\build"
```

### Step 2 - Build Mimikatz

Open `C:\Lab-Artifacts\mimikatz-src\mimikatz.sln` in Visual Studio 2022. Set the solution configuration to **Release** and platform to **x64**, then build with `Ctrl+Shift+B` (Build → Build Solution).

The output binary lands at:

```
C:\Lab-Artifacts\mimikatz-src\x64\Release\mimikatz.exe
```

Confirm the build succeeded before proceeding:

```powershell
Test-Path "C:\Lab-Artifacts\mimikatz-src\x64\Release\mimikatz.exe"
```

### Step 3 - Run ThreatCheck on Your Build

```cmd
C:\Lab-Artifacts\ThreatCheck\ThreatCheck.exe -f "C:\Lab-Artifacts\mimikatz-src\x64\Release\mimikatz.exe" -e Defender
```

ThreatCheck will binary-search the file and dump the byte range that triggers the first signature hit. Example output:

```
[!] Identified end of bad bytes at offset 0x1F3A0
[*] Dumping 256 bytes from offset 0x1F2A0

  Offset    00 01 02 03 04 05 06 07  ANSI
  --------  -----------------------  --------
  0x1F2A0   73 65 6B 75 72 6C 73 61  sekurlsa
  0x1F2A8   3A 3A 6C 6F 67 6F 6E 70  ::logonp
  ...
```

**Record the following before touching anything:**

- The file offset reported
- The readable strings in the ANSI column
- The source file those strings likely live in (a quick `grep -r` helps)

### Step 4 - Trace the Signature Back to Source

Use the string(s) from ThreatCheck's ANSI column to find their origin in the source tree:

```powershell
Select-String -Path "C:\Lab-Artifacts\mimikatz-src\*" -Pattern "sekurlsa" -Recurse
```

Common locations for tool-identifying strings:

| String pattern | Likely source file |
|---|---|
| Module/command names (`sekurlsa`, `lsadump`, `kerberos`) | `mimikatz/modules/m_*.c` or associated header |
| Banner/version strings | `mimikatz/mimikatz.c` |
| Help text and descriptions | Inline string literals near command dispatch tables |

### Step 5 - Patch the Signature

Once you know which source file and line carries the flagged string, modify it. Make the minimal change needed to remove the specific flagged bytes - do not refactor broadly, since you want to understand which change fixes which hit.

**Option A - Rename the string.** Change `"sekurlsa"` to something arbitrary (e.g., `"module01"`).

**Option B - Obfuscate at the string level.** Build the string at runtime via a char array so no static literal appears in the binary:

```c
// Before (static literal - easy to signature)
PWCHAR name = L"sekurlsa";

// After (runtime assembly - breaks static string match)
WCHAR name[] = { L's',L'e',L'k',L'u',L'r',L'l',L's',L'a',L'\0' };
```

**Option C - Strip or rename exported symbols.** Many Defender signatures key on PE export names; renaming them in the source removes that anchor.

### Step 6 - Rebuild

In Visual Studio use **Build → Clean Solution** followed by **Build → Build Solution**, or from the Developer Command Prompt:

```cmd
msbuild "C:\Lab-Artifacts\mimikatz-src\mimikatz.sln" /p:Configuration=Release /p:Platform=x64 /t:Clean,Build
```

### Step 7 - Re-run ThreatCheck

```cmd
C:\Lab-Artifacts\ThreatCheck\ThreatCheck.exe -f "C:\Lab-Artifacts\mimikatz-src\x64\Release\mimikatz.exe" -e Defender
```

One of three outcomes:

| ThreatCheck result | Meaning |
|---|---|
| New offset + new bytes reported | You fixed the first signature; Defender now trips on a different one. Go back to Step 4. |
| Same offset + same bytes | Your patch did not change those bytes in the output binary - re-check that you saved and rebuilt. |
| `[+] No threat found!` | Defender's static engine finds no remaining signature hits in this binary. |

### Rinse and Repeat

Each ThreatCheck run surfaces one signature boundary at a time. A mature AV engine like Defender often has **multiple independent signatures** for a well-known tool like Mimikatz - you may need to go through this loop a dozen or more times before you see a clean result.

Keep a running log as you work:

| Iteration | Offset | Flagged string / bytes | Source file patched | Result |
|---|---|---|---|---|
| 1 | `0x1F3A0` | `sekurlsa::logonp` | `modules/sekurlsa/sekurlsa.c` | New hit at `0x4A200` |
| 2 | `0x4A200` | `lsadump::dcsync` | `modules/lsadump/lsadump.c` | New hit at `0x8B100` |
| … | … | … | … | … |

This table becomes a map of Defender's signature coverage of the tool - which is itself valuable threat intelligence for a defender building detection rules.
